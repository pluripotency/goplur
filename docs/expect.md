# goexpect の基本機能と interact 実装に関する調査・技術解説

本書では、`goplur` の基盤となっている `goexpect`（`google/goexpect` のインライン移植版）の基本機能と、なぜ標準の `goexpect` だけでは対話（`interact`）機能を実現できず、`src/expect/interact.go` による拡張と端末（`term`）関連の制御が必要だったのかを詳しく解説します。

---

## 1. goexpect の基本機能

`goplur` の Expect エンジン（`src/expect/`）は、Google のオープンソースライブラリ `google/goexpect` からコアロジックを抽出・最適化したものです。主な機能は以下の通りです。

### 1.1 仮想端末（PTY）の生成とプロセスの起動 (`Spawn`)
- Linux の擬似端末（PTY: Pseudo-Terminal）ペア（Master / Slave）を生成します。
- 子プロセス（`ssh`, `bash`, `telnet` 等）を `setsid` / `setctty` でプロセスグループリーダーとして起動し、標準入出力を PTY Slave に接続します。
- これにより、端末が存在しないと動作しないコマンド（パスワードプロンプトや `sudo` など）も端末が接続されていると認識させて自動制御できます。

### 1.2 出力の監視とパターンマッチング (`Expect` / `ExpectSwitchCase`)
- PTY Master からバックグラウンドで出力を常時読み取り、内部バッファ（`e.out`）に蓄積します。
- 指定された正規表現リスト（`Caser`）と出力を照合し、一致したパターンのインデックスとマッチ文字列（キャプチャグループ含む）を返します。
- タイムアウト制御（`timerExpired`）を内蔵しており、指定時間内に期待するプロンプトが出現しない場合は安全にエラー終了します。

### 1.3 コマンド・キー入力の送信 (`Send`)
- チャネル（`e.snd`）を介して非同期に PTY Master へバイト列を書き込みます。
- 送信した文字列は PTY Slave を通じて子プロセスへ渡されます。

### 1.4 出力のログ転送 (`TeeWriter`)
- PTY Master から読み取った出力をリアルタイムに複製し、指定された `io.Writer`（`goplur` では標準出力およびファイルログ）へ転送します。

## 2. なぜ標準の goexpect だけでは interact を実現できないのか？

Python の `pexpect` には、スクリプトによる自動化から人間のキーボード操作へセッションの制御を引き渡す `child.interact()` という代表的なメソッドがあります。
しかし、**`google/goexpect`（および `netflix/go-expect` 等の Go 製 expect ライブラリ）には、この `interact()` に相当する機能が標準で存在しません。**

これには以下の技術的理由・アーキテクチャ上の理由があります。

### 理由 1: 「自動化テスト・スクリプト実行専用」の設計思想
`google/goexpect` は、CI/CD パイプラインやテスト環境、バッチスクリプト内での自動実行（プログラムから入力を送り、出力を検証する）を主目的として作られています。
そのため、「処理の途中で人間の操作に切り替える（Session Handoff）」というユースケースが設計段階で考慮されていません。

### 理由 2: 標準入力（`os.Stdin`）との直接接続が存在しない
`GExpect` はプロセス起動時に PTY Slave を子プロセスの Stdin に接続しますが、親プロセス側（`goplur` を実行している端末）の `os.Stdin` は一切接続されていません。`GExpect.Send()` はプログラムが生成した文字列をチャネル経由で渡すことしかできず、キーボード入力をリアルタイムにストリーミングする仕組みがありませんでした。

## 3. term（端末制御）関連の調査と課題

人間が端末から直接操作する対話モードを実現するには、単に `os.Stdin` を子プロセスに流し込むだけでは不十分であり、以下の Unix 端末（tty/termios）固有の課題を解決する必要があることが調査で判明しました。

### 3.1 Cooked モード（標準モード）の壁
通常のターミナル（Canonical / Cooked モード）では、OS の端末ドライバが以下のような処理を行っています：
1. **行バッファリング**: ユーザーが Enter キーを押すまで入力データがプログラムへ渡されない。
2. **ローカルエコー**: 入力した文字がローカル端末によって即座に画面に表示される。
3. **特殊シグナルのローカル処理**: `Ctrl+C`（SIGINT）や `Ctrl+Z`（SIGTSTP）を押すと、リモートのシェルではなく**手元の Go プログラム自身が終了・停止**してしまう。

このままでは、リモートシェルでの **Tab 補完、矢印キーによるカーソル移動、vim や nano の操作、Ctrl+C によるコマンド中断** が一切機能しません。

### 3.2 Raw モードへの移行と復元（`golang.org/x/term`）
対話モード中は、ローカル端末の入力を **Raw モード** に切り替える必要があります：
- `xterm.MakeRaw(int(os.Stdin.Fd()))` を呼ぶことで、入力のバッファリングとローカルエコーを無効化します。
- これにより、キーボードから入力された 1 バイト（Tab、エスケープシーケンス、Ctrl+C 等）が遅延なくそのまま取得され、PTY 経由でリモートシェルにダイレクトに送信されます。
- プロセス終了時には必ず `xterm.Restore()` を呼び、端末を元の Cooked モードへ戻さなければ、プログラム終了後にローカル端末の改行やエコーが壊れてしまいます。

### 3.3 ウィンドウサイズ（Winsize）の同期
PTY はデフォルトで 80 列 × 24 行などの固定サイズで起動されることがあります。
ユーザーの端末画面サイズ（例: 120 列 × 40 行）と PTY のサイズが一致していないと、長いコマンドを入力した際の折り返しや、`top`、`less`、`vim` などの全画面 TUI アプリケーションの描画が崩れます。
そのため、`xterm.GetSize` でローカル端末のサイズを取得し、`syscall.TIOCSWINSZ` ioctl を使って PTY Master の `Winsize` を同期する処理が必要になります。

### 3.4 リモート側のエコーバック（`stty echo` / `stty -echo`）の制御
`goplur` では、スクリプト自動化中に送ったコマンドがターミナルによって二重にエコーバック（重複表示）されるのを防ぐため、セッション開始時に `stty -echo` を設定しています。
しかし、この状態のままユーザーに対話権限を渡してしまうと、**ユーザーがキーボードを叩いても画面に何も文字が表示されなくなります**。
そのため、対話モードに入る直前に `stty echo` を送信してリモートのエコーを有効化し、対話終了時に必要に応じて戻すというセッション層での連携が不可欠でした。

## 4. `src/expect/interact.go` による解決

上記の課題を解決するため、`goplur` では既存の `expect.go`（goexpect のコアコード）を変更することなく、独立したモジュールとして [`src/expect/interact.go`](../src/expect/interact.go) を追加しました。

### 実装の役割分担

```
+--------------------------------------------------------------------+
|  example/ssh.go                                                    |
|  - 自動化シーケンス実行後、s.Interact() を呼び出す                 |
+---------------------------------+----------------------------------+
                                  |
                                  v
+---------------------------------+----------------------------------+
|  Session (src/session/interact.go)                                 |
|  - リモートエコー有効化 (stty echo)                                |
|  - 出力ライターのミュート解除 (Unmute)                             |
|  - s.child.Interact() を呼び出し                                   |
+---------------------------------+----------------------------------+
                                  |
                                  v
+---------------------------------+----------------------------------+
|  GExpect (src/expect/interact.go)                                  |
|  1. term.MakeRaw でローカル端末を Raw モードへ                     |
|  2. TIOCSWINSZ で端末ウィンドウサイズを同期                        |
|  3. os.Stdin の読み取りゴルーチンでキー入力を PTY Master へ転送     |
|  4. PTY 出力は既存の read/tee パイプラインでリアルタイム表示       |
|  5. 子プロセス終了検知 (for e.check())                             |
|  6. defer term.Restore でローカル端末を通常モードに安全復元        |
+--------------------------------------------------------------------+
```

### 提供されている API

1. **`GExpect.Interact() error`**
   `os.Stdin` と `os.Stdout` を使用して対話モードを開始します。子プロセスが終了（`exit` や `Ctrl+D`）するまでブロックし、終了後に端末を復元して制御を返します。
2. **`GExpect.InteractWithIO(in io.Reader, out io.Writer) error`**
   任意の入出力ストリームを接続できます。テストコードやパイプ経由での制御時にも柔軟に対応可能です。
3. **`Session.Interact() error`**
   セッション層のラッパーです。リモートエコーの調整を行った上で `GExpect.Interact()` を実行します。

---

## 5. まとめ

- **標準の `goexpect`**:
  自動テスト・スクリプト用の Expect/Send エンジンであり、端末の Raw モード制御や標準入力の直接接続（interact）は考慮されていなかった。
- **課題**:
  単に入力を繋ぐだけでは Cooked モードによるバッファリング、キー入力のローカル解釈、エコーの二重化/消失、ウィンドウサイズの不一致が発生する。
- **解決策**:
  `src/expect/interact.go` で `golang.org/x/term` と Linux PTY ioctl を統合し、端末の Raw モード化・サイズ同期・ストリーミング・安全な復元処理をカプセル化することで、Python の `pexpect.interact()` と同等のシームレスなセッション引き渡しを実現した。
